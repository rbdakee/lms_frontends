# Деплой фронтов

Локальный запуск — `README.md`. Здесь то, что отличает бой от разработки.
Бэкенд деплоится сам по себе, его правила — в его репозитории.

## Четыре деплоя, два сайта и админка

```
domain.kz         →  apps/web     (Vercel)   первая учебная площадка
<домен-2>         →  apps/web2    (Vercel)   вторая учебная площадка
admin.domain.kz   →  apps/admin   (Vercel)   одна админка на обе
api.domain.kz     →  бэкенд       (свой сервер, не Vercel)
```

Домен второй площадки владелец ещё не назвал. Везде ниже, где стоит
`<домен-2>`, подставляется он — и это единственное, чего не хватает третьему
деплою: приложение собирается и работает, проект в Vercel заводится за пять
минут по таблице ниже.

**Три проекта в Vercel из одного репозитория**, а не три репозитория: общий
`packages/ui` иначе пришлось бы публиковать приватным npm-пакетом и поднимать
версию в трёх местах на каждую правку кнопки. Vercel делит по проектам,
а не по репозиториям.

### Домены больше не обязаны быть роднёй

Раньше здесь было написано обратное — «все три обязаны быть поддоменами одного
домена, кука ставится на `.domain.kz`». **С переходом на две площадки это
неверно** (`../PLATFORMS_BRIEF.md`, решение 13): у площадок разные домены,
общего родителя у них нет, и кука сессии стала **host-only** — `COOKIE_DOMAIN`
не задаётся вовсе, каждый домен держит свою.

Что из этого следует:

- домен второй площадки может быть каким угодно — своим доменом, а не
  поддоменом первого; на вход это не влияет;
- **общего входа между площадками нет и не будет.** Аккаунт один — телефон
  и человек те же, — но войти надо на каждом домене отдельно. SSO не делаем;
- имя куки у приложений разное: `sid` у площадок, `sid_admin` у админки.
  Сервер выбирает его по `Origin` (`ADMIN_ORIGINS` в настройках бэкенда),
  поэтому в одном браузере одновременно живут вход админом и вход учителем.

Локально у этого есть видимое следствие, чинить которое не надо: порт в домен
куки не входит, поэтому на `localhost` обе площадки делят одну банку и вход
на `:3000` виден на `:3002`. В бою домены разные, и этого не будет.

## Настройки проекта в Vercel

Одинаково для всех трёх, отличаются только выделенные строки.

| Настройка | `web` | `web2` | `admin` |
|---|---|---|---|
| Root Directory | `apps/web` | `apps/web2` | `apps/admin` |
| Framework Preset | Next.js | Next.js | Next.js |
| **Install Command** | `npm ci --prefix ../..` | `npm ci --prefix ../..` | `npm ci --prefix ../..` |
| Build Command | по умолчанию (`next build`) | по умолчанию | по умолчанию |
| Ignored Build Step | `bash ../../scripts/vercel-ignore.sh web` | `bash ../../scripts/vercel-ignore.sh web2` | `bash ../../scripts/vercel-ignore.sh admin` |
| Домен | `domain.kz` | `<домен-2>` | `admin.domain.kz` |

Три места, где Vercel нужно поправить руками:

- **Install Command переопределяется на `npm ci --prefix ../..`.** Это не
  украшение: с командой по умолчанию Vercel ставит зависимости внутри папки
  приложения, не видит `typescript` и `@types/*` из `devDependencies` корня
  воркспейса, и сборка падает на проверке типов. 21.08.2026 на этом упали
  первые две сборки подряд, прежде чем причину нашли.
- **Include source files outside of the Root Directory** — включено. Без этого
  сборка не увидит `packages/` и упадёт на первом импорте `@lms/ui`.
- **Тариф.** Hobby у Vercel некоммерческий, а курсы платные, — значит Pro.
  Счёт считается за участников команды, а не за проекты: третий проект
  не увеличивает его.

### Ignored Build Step

`scripts/vercel-ignore.sh` — коммит, задевший только админку, пересобирает
только админку. Правка в `packages/` задевает все три приложения и пересобирает
все три; первый деплой собирается всегда.

Скрипт принимает имя папки в `apps/`, поэтому третий проект работает без правки
скрипта — `vercel-ignore.sh web2` и всё.

Сравнение идёт с **последней удачной сборкой этого проекта**
(`VERCEL_GIT_PREVIOUS_SHA`, Vercel отдаёт её только внутрь Ignored Build Step),
а не с `HEAD^`. В пуше почти всегда несколько коммитов, и по `HEAD^` пропуск
считался по последнему из них: пуш, где последний коммит трогал только админку,
оставлял клиентское приложение на старой сборке вместе со всеми правками ниже.

Договорённость Vercel обратная привычной: выход `0` — сборку **пропустить**.

## Переменные окружения

`NEXT_PUBLIC_*` подставляются **в момент сборки**, а не читаются при запуске:
значение попадает прямо в js-файлы. Отсюда два следствия — задать их нужно
до первой сборки, а изменить их значит пересобрать, а не перезапустить.

| Переменная | `web` | `web2` | `admin` | Что это |
|---|---|---|---|---|
| `NEXT_PUBLIC_API_URL` | `https://api.domain.kz` | `https://api.domain.kz` | `https://api.domain.kz` | единственная дорога на бэкенд (`packages/api/client.ts`) |
| `NEXT_PUBLIC_ADMIN_URL` | `https://admin.domain.kz` | `https://admin.domain.kz` | — | ссылки в админку с клиентских экранов (`apps/web*/lib/urls.ts`) |
| `NEXT_PUBLIC_WEB_URL` | — | — | `https://domain.kz` | ссылки на клиентские экраны из админки (`apps/admin/lib/urls.ts`) |

**Переменной с кодом площадки нет и заводить её не нужно.** Площадку сервер
узнаёт по `Origin` запроса: каталог, цены, доступы, прогресс и сертификаты
фильтруются на сервере, а не на фронте. Второе приложение отличается от первого
доменом, темой и брендом — и ничем больше.

`NEXT_PUBLIC_WEB_URL` у админки одна, а площадок две: ссылка из админки ведёт
на первую. Ссылок «открыть на второй площадке» в админке пока нет; появятся —
понадобится вторая переменная.

Те же переменные с боевыми значениями лежат образцами рядом с самими
приложениями: `apps/web/.env.example`, `apps/web2/.env.example`,
`apps/admin/.env.example`.

Локально они не нужны вовсе: умолчания в коде — это `localhost:8000`,
`localhost:3001` и `localhost:3000`.

Секретов среди них нет и быть не может: всё, что с приставкой `NEXT_PUBLIC_`,
уезжает в браузер. Ключи, токены и пароли живут только на бэкенде.

## Выкат второго домена — шагами

Первая площадка в это время работает, и ни одного шага, который бы её задел,
здесь нет. Порядок важен: бэкенд узнаёт про домен **до** того, как домен начнёт
отвечать, иначе первый же зашедший увидит каталог первой площадки.

1. **Назвать домен.** Всё дальнейшее — подстановка его вместо `<домен-2>`
   в шести местах: три строки `.env` бэкенда, один домен в Vercel, одна запись
   DNS и переменные проекта.
2. **Бренд второй площадки — до выката, а не после.** Пока он не заменён,
   в шапке стоит «Вторая площадка», в подвале `+70000000002`, а сертификаты
   выходят подписанными плейсхолдером. Меняется в двух местах:
   - `apps/web2/lib/brand.ts` — название RU/KZ и почта поддержки,
     `apps/web2/lib/logo.svg` — знак площадки;
   - на бэкенде `app/domain/brands.py` (`BRANDS[P2]`) и четыре картинки
     в `app/assets/brands/p2/`.
3. **Бэкенд: три строки в `.env`** (подробности — `DEPLOY.md` бэкенда, раздел
   «Домен второй площадки»):
   - `CORS_ORIGINS` — дописать `https://<домен-2>`;
   - `PLATFORM_ORIGINS` — дописать `"https://<домен-2>": "p2"`. Забыть
     не смертельно на вид и потому опасно: сервис поднимется, а вторая
     площадка молча покажет каталог, доступы и сертификаты первой;
   - `PLATFORM_VERIFY_URLS` — `{"p1": "https://domain.kz", "p2": "https://<домен-2>"}`.
     Забыть — печатать на бумажных сертификатах второй площадки QR, ведущий
     на первую, где проверка честно ответит «не найдено».

   Перезапуск обычный, миграций нет. Проверка:
   ```sh
   curl -s -H "Origin: https://<домен-2>" https://api.domain.kz/settings | head -c 200
   ```
   Должно прийти имя **второй** площадки.
4. **Третий проект в Vercel** — по таблице выше. Root Directory `apps/web2`,
   Install Command `npm ci --prefix ../..`, Ignored Build Step
   `bash ../../scripts/vercel-ignore.sh web2`, обе переменные `NEXT_PUBLIC_*`.
   Собрать и убедиться, что сборка зелёная, **до** привязки домена: на
   `*.vercel.app` приложение уже открывается, только API его туда не пустит
   (этого источника нет в `CORS_ORIGINS`, и это нормально).
5. **DNS.** Запись на Vercel по его инструкции. **Отрицательный ответ у PS.KZ
   кешируется час** (`SOA minimum 3600`): после заведения записи браузер
   и роутер ещё час говорят «домена нет». Это не сломанный деплой и не повод
   что-то переделывать; лечится сменой резолвера на `1.1.1.1`, а не
   перезапуском сборки.
6. **Сквозняк по живому домену**, в этом порядке: открыть → войти по коду →
   каталог → заявка → админ выдаёт доступ **на второй площадке** → урок → тест →
   сертификат → проверить его номер по QR.
7. **Проверить развязку площадок:** номер сертификата первой площадки на второй
   отвечает «не найдено», и наоборот. Это не баг, а решение 10 договорённости.
8. **Проверить, что первая площадка не изменилась** — шапка, подвал, каталог,
   вход, скачивание сертификата.

## Порядок первого выката

1. Бэкенд поднят и отвечает на `https://api.domain.kz/health` — иначе первый же
   экран фронта покажет ошибку сети.
2. `CORS_ORIGINS` на бэкенде содержит адреса **всех** фронтов, `PLATFORM_ORIGINS`
   называет площадку каждого учебного домена, `PLATFORM_VERIFY_URLS` — адрес
   проверки каждой площадки. `COOKIE_DOMAIN` не задаётся вовсе: кука host-only.
3. Проекты в Vercel заведены, Root Directory, Install Command и переменные
   заданы.
4. Домены привязаны, DNS указывает на Vercel.
5. Проверить руками вход: `domain.kz/login` → код → `/me` отвечает. Не отвечает —
   смотреть куку в инструментах браузера: чаще всего это `COOKIE_SECURE` или
   адрес, которого нет в `CORS_ORIGINS`. `Domain=` у куки быть не должно: она
   ставится на тот домен, который её выдал.
6. Проверить, что стороны развязаны: войти в админку и убедиться, что вход
   в кабинете учителя остался живым. Выбило — на бэкенде не задан
   `ADMIN_ORIGINS`, и админка получила ту же куку, что и кабинет.

Отдельное ограничение первого выката, о котором нужно знать до раздачи адреса
людям: **настоящего SMS-провайдера у бэкенда нет**, код входа печатается в его
лог. Учитель войти не может — вход есть только у админа (подробности в
`DEPLOY.md` бэкенда). Каталог при этом виден всем: он открытый и входа
не требует.

## Проверки перед выкатом

```sh
npm run typecheck
npm run build
```

Обе команды проходят по **трём** приложениям. Сборка проверяет и типы, но
`typecheck` отвечает быстрее и говорит понятнее. Типы ответов API генерируются
из OpenAPI-схемы бэкенда — разошедшийся контракт всплывает здесь, а не
на экране.
